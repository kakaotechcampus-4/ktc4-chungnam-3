## 배경
현재 백엔드는 Java·Spring Boot 기반이며 Spring AI와 Gemini를 사용하고 있다. MVP에서는 이 구조를 활용해 에이전트를 먼저 구현하고, 실제 실행 결과를 보면서 필요한 기능을 추가한다.

## 대안 비교

| 대안                      | 제공하는 기능과 장점                                                                   | 선택 시 고려사항                                                                       |
| ----------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Spring AI               | 모델 호출, 도구 실행과 반복 호출, 구조화된 응답을 지원한다. 기존 Spring 설정과 서비스 메서드, 측정·추적 체계를 활용하기 좋다. | 복잡한 단계 분기와 중간 상태 저장은 별도로 설계해야 한다.                                               |
| LangChain4j             | Java 인터페이스로 AI 서비스를 선언하고 도구·RAG·메모리·응답 변환을 연결할 수 있다. Spring Boot 통합도 지원한다.    | 현재 요구는 기본 AI Services로 구현할 수 있다. 선언형 API의 장점과 기존 모델·도구 연결을 새로 구성하는 작업을 함께 고려한다. |
| Spring AI + LangGraph4j | 실행 단계를 그래프로 표현하고 조건 분기, 중간 상태 저장, 중단 후 재개를 관리할 수 있다.                          | 단계·연결·공유 상태를 설계해야 하며 학습할 개념이 늘어난다.                                              |

Spring AI와 LangChain4j 모두 현재 필요한 도구 호출 에이전트를 구현할 수 있는 유효한 선택지다. LangChain4j의 기본 AI Services로 도구 호출과 응답 변환을 구성할 수 있으며, 전용 agentic 모듈은 이 구성에 필수적이지 않다.
LangChain4j는 Python LangChain과 독립된 Java 라이브러리로, API와 릴리스 주기가 다르다. 선택은 현재 Java 프로젝트에 필요한 기능과 개발 방식을 기준으로 비교한다.
LangGraph4j는 Spring AI와 함께 사용할 수 있는 흐름 관리 도구다. 따라서 현재 기술 선택과 이후 흐름 관리 도입을 나누어 결정할 수 있다.

## 결정

꺼내기 에이전트는 우선 Spring AI로 구현한다.

- 기존 RecallAgent 인터페이스를 유지하고 Spring AI를 사용하는 구현체를 추가한다.
- ChatClient에 판단 기준과 도구를 제공한다. 모델이 도구를 선택하면 Spring AI가 실행 결과를 돌려주고 필요한 조회를 반복한다.
- 후보 조회 등 서버의 서비스 메서드를 도구로 제공하고, 최종 판단을 기존 에이전트 결과 형식으로 반환한다.
- 회원 소유권과 결과 검증, 실행 상태 변경, 알림 저장·전송은 기존 서버 책임으로 유지한다.

현재 필요한 후보 조회와 추가 검색, PROPOSE/NO_ACTION 반환은 Spring AI와 LangChain4j 모두 구현할 수 있다. LangChain4j의 인터페이스 중심 API도 적합하지만, 이번 MVP에서는 이미 연결된 Spring AI 모델과 Spring 기반 설정을 활용하고 실행 시간·도구 호출 측정까지 같은 관측 체계에 연결하는 것을 우선한다.

현재 요구를 충족하는 기술이 이미 프로젝트에 있으므로 통합 작업을 줄이고 실제 에이전트의 판단 품질과 실행 시간을 먼저 평가하기 위해 Spring AI를 채택한다. 이후 구체적인 기능 요구가 생기면 대안을 다시 검토한다.

판단 기준, 도구의 입력·출력, 호출 횟수와 시간 제한, 실패 처리 및 평가 방법은 에이전트 설계에서 별도로 정한다.

## 추후 LangGraph4j 검토 조건

실제 구현과 측정 과정에서 다음 요구가 생기면 LangGraph4j 도입을 검토한다.

- 검색·검토·재검색 등 여러 단계의 조건 분기를 명시적으로 관리해야 한다.
- 실행 도중의 상태를 저장하고 중단된 지점부터 재개해야 한다.
- 단계별 상태와 전이 로직이 복잡해져 서비스 코드에서 관리·추적하기 어려워진다.

도입 시에는 Spring AI의 모델·도구 연결을 활용하면서 그래프 기반 흐름 관리를 추가한다. RecallAgent 인터페이스를 유지해 기존 이벤트·실행·알림 처리에 미치는 영향을 줄인다.
