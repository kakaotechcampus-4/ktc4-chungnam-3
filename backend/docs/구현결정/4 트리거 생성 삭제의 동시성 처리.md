# 트리거 생성·삭제의 동시성 처리

## 문제

트리거는 두 경로에서 생성되고 한 경로에서 삭제된다. 이들이 동시에 실행되면 트리거가 누락되거나 잘못 남는다.

**저장 vs 분석 완료**

저장은 PersonalSave를 쓰고 Content 상태를 읽는다. 분석 완료는 Content를 쓰고 PersonalSave를 읽는다. 두 트랜잭션이 겹치면 서로의 미커밋 데이터를 보지 못해 양쪽 모두 트리거를 만들지 않는다.

**저장 vs 삭제**

저장은 PersonalSave를 쓰고 트리거 존재를 읽는다. 삭제는 PersonalSave를 지우고 남은 저장물을 읽어 트리거 삭제를 판단한다. 두 트랜잭션이 겹치면 저장물은 있는데 트리거가 없거나, 저장물이 없는데 트리거가 남는다.

두 경우 모두 각 트랜잭션은 혼자서는 옳지만, 서로 다른 행을 쓰면서 상대가 쓰는 값을 전제로 판단해 합쳐진 결과가 틀리는 write skew다.

## 대안 비교

| 방식                   | 동작                                 | 장점                            | 단점                                      |
| -------------------- | ---------------------------------- | ----------------------------- | --------------------------------------- |
| 낙관적 락                | 같은 행의 버전을 비교해 충돌 감지                | 충돌이 드물 때 대기 비용이 없다            | 두 트랜잭션이 같은 행을 수정하지 않으므로 충돌을 감지하지 못한다    |
| SERIALIZABLE         | DB가 write skew를 감지해 한쪽을 롤백         | 코드에서 순서를 관리하지 않아도 된다          | 모든 트랜잭션에 충돌 추적 비용이 붙고, 실패 시 재시도 로직이 필수다 |
| 트리거를 저장하지 않고 조회 시 계산 | PersonalSave와 ContentPlace에서 매번 도출 | 경쟁 자체가 사라진다                   | 지오펜스 조회가 무거워진다(드문 경쟁에서 굳이)              |
| 조회 시 누락 트리거 재생성      | 깨져도 다음 조회에서 복구                     | 락 로직이 필요 없다                   | 조회마다 정합성 확인 비용이 붙고, 복구 전까지는 누락 상태다      |
| 공통 부모 행 비관적 락        | 둘 다 판단 근거로 쓰는 행을 먼저 잠가 순서를 강제      | 재시도 로직이 필요 없고 이미 같은 패턴을 쓰고 있다 | 락 순서를 코드로 관리해야 한다                       |

## 선택

공통 부모 행을 비관적 락으로 잠근다.

- 저장 vs 분석 완료는 Content 행으로 직렬화한다.
- 저장 vs 삭제는 Member 행으로 직렬화한다.

## 락 순서

저장과 삭제는 두 락을 모두 잡는다. 순서가 다르면 서로 상대가 쥔 락을 기다리는 데드락이 발생하므로 항상 Member → Content 순서로 잡는다.

분석 완료는 Content만 잡으므로 이 순서와 충돌하지 않는다.

저장 경로의 claimAnalysis는 PENDING일 때만 UPDATE로 행을 잠그므로, 이미 ANALYZING이나 종료 상태인 콘텐츠도 잠그려면 상태 확인 전에 SELECT ... FOR UPDATE로 명시적으로 잠근다.
