# 콘텐츠 저장 및 분석 구현 방향

## 전체 흐름

```text
YouTube URL 저장 요청
→ 인증 객체에서 memberId 조회
→ URL 정규화 및 videoId 추출
→ Content와 PersonalSave 저장
→ Content 분석 선점
→ YouTube 메타데이터 및 Gemini 분석
→ 분석 결과 저장
```

1. 유효하지 않은 URL은 저장하지 않음.
2. `Content`가 없으면 `PENDING` 상태로 생성.
3. `PersonalSave`를 먼저 생성해 사용자의 저장 의도를 보존.
4. `PENDING → ANALYZING` 조건부 갱신에 성공한 요청만 저장 파이프라인 호출.
5. 분석 결과에 따라 `SUCCESS`·`PARTIAL`·`FAILED`로 변경.
6. 분석에 실패해도 `PersonalSave`는 유지.

## 기술 선택

|문제|선택|대안|선택 이유|
|---|---|---|---|
|중복 생성 방지|UNIQUE 제약 + PostgreSQL `ON CONFLICT DO NOTHING`|낙관적 락, 조회 후 INSERT|낙관적 락은 이미 존재하는 행의 동시 수정만 감지하므로 아직 없는 콘텐츠의 동시 INSERT는 못 막음. DB UNIQUE 제약으로 중복을 차단하고, 충돌한 요청은 기존 데이터를 조회.|
|분석 중복 실행 방지|상태 조건부 UPDATE|비관적 락, Redis 분산 락|동일 콘텐츠 동시 저장이 빈번하지 않아 비관적 락으로 요청을 대기시킬 필요 없음. 현재 단일 서버라 Redis 분산 락도 불필요. 상태 조건부 UPDATE만으로 한 요청이 분석 선점 가능.|
|분석 실행|동기 호출|Spring 비동기 이벤트, 메시지 브로커, DB 작업 큐|현재는 요청에서 분석 완료까지 기다려도 되는 구조라 동기 호출이 더 단순. 비동기 이벤트 유실·별도 작업 처리 구조를 만들지 않고, 실제 응답시간 측정 후 비동기 전환 여부 결정.|

## 서비스 경계

외부에 제공하는 저장 유스케이스는 하나.

```text
save(memberId, youtubeUrl)
```

- `memberId`는 요청 DTO로 받지 않고 인증 객체에서 가져옴.
- 저장 파이프라인도 분석 메서드 하나만 제공.

```text
analyze(videoId) → AnalysisOutcome
```

`AnalysisOutcome`은 아래 결과 중 하나와 분석 데이터를 포함.

- `SUCCESS`
- `PARTIAL`
- `FAILED`

## 트랜잭션 경계

```text
짧은 트랜잭션
→ Content 및 PersonalSave 저장
→ Content 분석 선점
→ 트랜잭션 종료

트랜잭션 없음
→ YouTube 및 Gemini 외부 API 호출

짧은 트랜잭션
→ 분석 결과와 최종 상태 저장
```

외부 API 호출을 포함한 전체 저장 흐름에 하나의 트랜잭션을 걸지 않는다. 분석 응답을 기다리는 동안 DB 커넥션과 락을 점유할 수 있기 때문.

## 동시성 처리

- `Content.videoId`에 UNIQUE 제약 적용. 같은 영상이 동시에 저장되면 `ON CONFLICT DO NOTHING`으로 중복 생성 방지, 충돌한 요청은 `videoId`로 기존 `Content` 조회.
- `PersonalSave`에는 `UNIQUE(member_id, content_id)`를 적용해 같은 사용자의 중복 저장 방지.

분석 선점은 아래 조건을 만족할 때만 성공.

```sql
UPDATE content
SET analysis_status = 'ANALYZING',
    analysis_started_at = CURRENT_TIMESTAMP
WHERE id = :contentId
  AND analysis_status = 'PENDING';
```

갱신된 행이 1건인 요청만 저장 파이프라인을 호출한다. 나머지 요청은 현재 `Content` 상태를 반환하고 같은 콘텐츠를 다시 분석하지 않는다.

## 동기 처리의 한계

- YouTube·Gemini 응답을 기다리는 동안 HTTP 요청 스레드가 점유됨. 우선 실제 영상으로 전체 응답시간과 타임아웃 발생 여부를 측정한다.
- 응답시간이나 동시 요청 문제가 확인되면 Spring 비동기 처리, DB 작업 큐, 메시지 브로커 도입 검토.
- 분석 도중 서버가 종료되면 `ANALYZING` 상태가 남을 수 있어 `analysisStartedAt`을 기록한다. 자동 재시도·재선점 정책은 실제 분석 시간과 실패 형태를 측정한 뒤 결정.
