# 애플리케이션 - Java, Spring Boot

백엔드와 꺼내기 에이전트를 모두 Java와 Spring Boot로 구현합니다.

꺼내기 에이전트가 사용하는 도구는 주로 데이터베이스를 조회하거나 외부 API를 호출하는 기능입니다. 현재 범위에서는 Spring AI의 도구 호출 기능으로 구현할 수 있으며, Python 생태계를 사용함으로써 얻는 명확한 이점은 확인되지 않았습니다.
에이전트를 Spring 애플리케이션의 내부 모듈로 구현하면 별도의 서비스 통신과 배포가 필요하지 않고, 로그와 장애 흐름도 한곳에서 추적할 수 있습니다. 팀원들이 Java에 익숙하고 개발 기간이 제한된 점도 고려했습니다.
기능 경계는 코드상 모듈로 분리하고, 이후 Java에서 구현하기 어려운 요구사항이 확인될 경우 별도 서비스 분리를 다시 검토합니다.

# DB - PostgreSQL

사용자, 저장 콘텐츠, 장소, 행사 정보, 알림 이력 등이 서로 참조되므로 관계와 데이터 정합성을 관리하기 적합한 관계형 데이터베이스가 필요합니다.
또한 꺼내기 에이전트는 다음 두 종류의 검색을 사용합니다.

- 현재 위치를 기준으로 주변의 검증된 장소 검색
    
- 콘텐츠 요약의 임베딩을 이용한 의미 유사도 검색

이에 따라 PostgreSQL에 PostGIS와 pgvector 확장을 적용하는 구성을 선택했습니다.

- **PostgreSQL:** 사용자·저장물·장소·알림 이력 등의 관계형 데이터 관리
    
- **PostGIS:** 현재 위치와 장소 좌표를 이용한 거리·반경 검색
    
- **pgvector:** 콘텐츠 요약 임베딩 저장과 의미 유사도 검색. 어떤 저장물이 지금 어울리는지는 카테고리나 거리보다 요약에 담긴 의미에 더 강하게 드러나기 때문입니다.
    

이를 통해 사용자, 유효 상태, 최근 알림 여부, 위치 반경, 의미 유사도 등의 조건을 하나의 데이터베이스에서 함께 처리할 수 있습니다.

# 푸시 알람 - FCM

지오펜스 이벤트가 발생하면 앱은 서버에 꺼내기 실행을 요청합니다.  
꺼내기 에이전트는 Gemini와 외부 도구를 호출하므로 실행시간이 일정하지 않습니다. 앱이 결과를 받을 때까지 HTTP 연결을 유지하면 백그라운드 실행 제한, 네트워크 변경과 요청 시간 초과의 영향을 받을 수 있습니다.  
따라서 앱에는 `202 Accepted`와 실행 식별자를 먼저 반환하고, 서버가 꺼내기 실행을 비동기로 완료한 뒤 Firebase Cloud Messaging을 통해 결과를 전달합니다.

지오펜스 이벤트 발생 → 앱이 서버에 실행 요청 → 서버가 RecallExecution 생성 → 앱에 202 Accepted 반환 → 서버가 꺼내기 에이전트 실행 → PROPOSE이면 Notification 생성 → FCM으로 푸시 알림 전송

## 검토한 대안

### MySQL과 별도 벡터 데이터베이스

MySQL에 일반 데이터와 위치 정보를 저장하고, Qdrant나 Elasticsearch 같은 별도 저장소에서 벡터 검색을 수행하는 방식입니다.
각 저장소를 목적에 맞게 독립적으로 확장할 수 있지만, 콘텐츠 생성·수정·삭제 시 두 저장소를 함께 갱신해야 합니다. 한쪽만 반영될 경우 데이터가 어긋날 수 있어 동기화와 실패 복구가 추가로 필요합니다.
현재는 벡터 검색량이 이러한 운영 복잡성을 감수할 정도로 크다고 판단할 근거가 없어 선택하지 않았습니다.

### MongoDB Atlas

Gemini의 분석 결과를 JSON과 유사한 문서 구조로 저장하기 편하고, 지리 검색과 벡터 검색도 지원합니다.
그러나 우리 서비스는 추출 결과를 그대로 보관하는 데서 끝나지 않고, 사용자·저장물·검증된 장소·행사·알림 이력 사이의 관계를 지속적으로 관리해야 합니다. 이런 구조에는 문서형 데이터베이스보다 관계형 데이터베이스가 더 자연스럽다고 판단했습니다.

### PostgreSQL과 별도 검색 저장소

일반 데이터는 PostgreSQL에서 관리하고, 임베딩 검색만 Elasticsearch나 전용 벡터 데이터베이스로 분리하는 방식입니다.
벡터 데이터와 검색 요청이 크게 증가하면 검색 부분만 독립적으로 확장할 수 있다는 장점이 있습니다. 반면 MVP 단계에서는 저장소 간 데이터 복제와 동기화, 별도 배포와 모니터링이 필요해집니다.
따라서 현재는 pgvector를 사용하고, 검색량과 응답시간을 측정한 뒤 필요할 경우 분리하기로 했습니다.

### Redis 또는 Elasticsearch를 이용한 공간 검색

장소 좌표를 Redis나 Elasticsearch에 별도로 저장하고 주변 장소를 검색하는 방식입니다.
Redis는 단순한 거리·반경 검색을 빠르게 처리할 수 있고, Elasticsearch는 위치 검색을 벡터·텍스트 검색과 함께 처리할 수 있습니다.
하지만 원본 장소 데이터는 PostgreSQL에 있으므로 좌표와 상태 변경을 별도 저장소에도 반영해야 합니다. 저장소 간 동기화와 장애 복구, 별도 배포와 모니터링도 필요합니다.
현재 규모에서는 이러한 복잡성을 감수할 근거가 없으므로 PostGIS를 사용하고, 위치 검색량과 응답시간이 증가할 경우 별도 검색 저장소 도입을 검토합니다.

## 결론

MVP에서는 PostgreSQL, PostGIS, pgvector를 이용해 관계형 데이터와 위치·임베딩 데이터를 하나의 데이터베이스에서 관리합니다.
향후 벡터 수와 검색 요청이 증가해 목표 응답시간을 충족하지 못하거나, 검색 기능을 독립적으로 확장해야 할 필요가 확인되면 별도의 검색 저장소와 별도 기술을 검토합니다.
