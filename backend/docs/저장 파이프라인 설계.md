# 저장 파이프라인 설계

이 문서는 "저장담당" 역할의 **구현 설계**다. 무엇을 반환해야 하는지(계약)는 `저장담당 요구 사항.md`에 이미 정리돼 있고, 이 문서는 그걸 어떻게 만들 것인지를 다룬다.

## 1. 배경 — 왜 "에이전트"가 아니라 "파이프라인"인가

원래 "저장 에이전트"로 불렸고, `트러블슈팅- Elice API.md`의 "최종 선택안"에도 "장소검색 API를 도구로 스스로 선택해 재검색/확인을 판단하는" 에이전틱한 구조로 적혀 있다.

하지만 실제로 필요한 건 정해진 순서(메타데이터 조회 → 영상 분석 → 장소 검색 → 확신도 판정)를 그대로 실행하는 것이고, 매 단계 무엇을 할지 스스로 선택하는 자율성이 필요하지 않다고 판단해 **"저장 파이프라인"으로 이름을 바꾸기로 했다.** LLM 호출은 "영상 분석" 한 단계에서만 일어나고, 그마저도 정해진 프롬프트·스키마로 고정된 호출이지 도구를 선택하는 루프가 아니다.

> ⚠️ **문서 불일치 메모**: `트러블슈팅- Elice API.md`의 4장은 아직 에이전틱(도구 자율 선택) 구조로 적혀 있다. 팀에 공유해서 필요하면 그 문서도 업데이트할지 논의할 것. (기술적 결론 — Vertex AI 사용, ADC 인증, 장소검색 API를 도구로 쓴다는 것 — 은 이 문서와 동일하다. 바뀐 건 "누가/무엇이 다음 행동을 결정하는가"뿐이다.)

"꺼내기 에이전트"는 여전히 진짜 에이전트다 (지오펜스 트리거 이후 가설을 세우고 도구를 골라 쓰고 계획을 바꾸는 자율 루프). 저장 쪽만 파이프라인으로 바뀐 것이다.

## 2. 이 파이프라인의 책임 범위

`docs/카테켐프로젝트 개요.md`의 "역할과 책임"을 따른다.

**한다:**
- 유튜브 URL 하나를 받아서 영상 분석
- 장소 후보를 실제 장소검색 API로 탐색·검증 (좌표 확보)
- 확신도가 낮고 후보를 좁힐 수 있으면 사용자 확인 요청 반환
- 위 결과를 Spring 코어에 반환

**안 한다:**
- DB 저장 (Spring 코어 책임)
- 트리거 생성/저장 (Spring 코어 책임 — 파이프라인은 "검증된 장소"까지만 반환하고, 그걸 트리거로 만드는 건 Spring이 한다)
- 알림 발송, 꺼내기 판단 (꺼내기 에이전트 책임)
- 원본 영상·음성·전체 자막 저장 (정책상 저장 안 함 — 메타데이터/짧은 요약/검증된 장소만 저장)

## 3. 전체 흐름

```text
YouTube URL 입력 (Spring이 URL 검증·정규화 완료 후 파이프라인 호출)
  ↓
[1] 메타데이터 조회 — YouTube Data API v3 (videos.list, commentThreads.list)
  ↓
[2] 영상 분석 — Vertex AI Gemini (영상 URL 직접 입력 + 텍스트 컨텍스트)
  │    → 요약, 태그, 장소 후보(미확정), 기간 정보, 근거(evidence)
  ↓
[3] 장소 탐색·검증 — 장소검색 API (미정, 아래 6장 참고)
  │    장소 후보 이름/지역 힌트로 검색 → 실제 장소 매칭 시도
  ↓
[4] 판정
  ├─ 장소 1건으로 확정됨            → PLACE_RESOLVED
  ├─ 후보 복수 & 2~3개로 좁혀짐      → NEEDS_CONFIRMATION (질문+선택지 포함)
  ├─ 후보 있으나 확정 불가(재검색 실패) → NO_PLACE (정보 없음과 동일하게 취급 — 추측 금지)
  └─ 애초에 장소 후보 없음           → NO_PLACE
  ↓
결과 반환 → Spring이 형식·필수값 검증 → 장소 확정 시에만 위치 트리거 생성 → DB 저장
```

**핵심 원칙 (기존 설계에서 유지):**
- 정보가 없으면 만들지 않는다 — 좌표를 추측해서 채우지 않는다. 트리거 0개는 실패가 아니라 정상 경로다.
- 되묻기는 콘텐츠당 최대 1회. 파이프라인은 상태를 갖지 않으므로, "이미 물어봤는지"는 Spring이 관리해서 매 호출마다 넘겨줘야 한다.
- 기간(일정) 기반 트리거는 MVP 범위 밖 (`카테켐프로젝트 개요.md` 3장). 기간 정보는 추출은 하되(향후 확장 대비, `TemporalInfoDto`), 트리거로 연결하지 않는다.

## 4. 단계별 상세

### 4.1 메타데이터 조회

- YouTube Data API v3, API 키만으로 REST 직접 호출 (공식 자바 클라이언트는 OAuth 위주라 이 용도엔 과함 — 오늘 실제로 이렇게 구현해서 검증함)
- `videos.list` (part=snippet,contentDetails): 제목, 설명, 태그, 채널ID, 길이
- `commentThreads.list`: 채널 소유자(작성자)가 단 댓글만 필터링해서 사용 — 주소를 직접 답글로 남기는 경우가 많아 장소 신호로 유용

### 4.2 영상 분석

- **Vertex AI Gemini**를 사용한다 (Elice ML API는 영상/파일 입력 및 Interactions API를 지원하지 않아 배제됨 — `트러블슈팅- Elice API.md` 참고).
- 인증: 로컬 개발은 ADC(`gcloud auth application-default login`), 배포 환경은 서비스 계정.
- 유튜브 URL을 영상으로 직접 전달 (다운로드 안 함 — 정책상 안전, Google 인프라가 처리).
- 구조화 출력(JSON 스키마)으로 요약/태그/장소후보/기간정보/근거를 한 번에 받는다.
- **오늘 실제로 검증한 내용** (raw `com.google.genai` SDK로, 모델 `gemini-3.8-flash` 기준):
  - `generateContent`(레거시지만 안정적)로 유튜브 URL을 `Part.fromUri(url, "video/mp4")`로 전달하면 동작함
  - 최신 "Interactions API"(`client.interactions`)는 아직 Vertex AI에서 불안정함(문서에 "coming soon", 커뮤니티에 404 보고 다수) — **`generateContent` 사용을 권장**
  - 영상 1건 분석 시 입력 토큰 약 5,800~6,000개, 응답시간 20~30초 (가끔 할당량/과부하로 더 오래 걸리거나 429/503 발생)
  - `트러블슈팅- Elice API.md`의 실측치(모델 2.5 Flash Lite 기준, 영상 3,354 + 음성 350 = 총 3,927 토큰, 1원 미만)와는 모델이 달라 직접 비교는 안 되지만, 같은 방식(영상 URL 직접 입력)이 잘 동작한다는 점은 일치함
- **TODO — 검증 필요**: 이 프로젝트는 `spring-ai-starter-model-google-genai`(Spring AI)를 이미 채택했다. 오늘 검증은 raw SDK로 했고, **Spring AI의 `ChatClient`/`ChatModel` 추상화로 "유튜브 URL을 영상으로 전달 + JSON 스키마 구조화 출력"이 어떻게 표현되는지는 아직 확인 안 함.** 실제 구현 시작 전에 Spring AI 문서/소스로 확인 필요.

### 4.3 장소 탐색·검증

- 장소 후보(이름/지점힌트/지역힌트)를 장소검색 API에 질의해서 실제 장소로 매칭 — 좌표와 주소 확보.
- 검색 결과가 애매하면(동명 장소 다수 등) 검색어를 좁혀 재검색하거나, 그래도 안 되면 사용자 확인 요청으로 넘긴다.
- **TODO — 미정**: 어떤 장소검색 API를 쓸지 아직 팀 문서 어디에도 명시되지 않음 (`선택한 기술.md`에도 없음). 카카오 로컬 API / Google Places API 등 후보 중 확인 필요.

### 4.4 확신도 판정 및 사용자 확인

- 규칙: 확신도가 낮고(임계값 미정) 후보를 2~3개로 좁힐 수 있을 때만 `NEEDS_CONFIRMATION`.
- 되묻기는 콘텐츠당 최대 1회 — 파이프라인은 무상태이므로 "이미 물어봤는지"를 Spring이 호출 시 파라미터로 넘겨줘야 한다.
- 미응답 시 상위 지역으로 저장, 다시 묻지 않음 (Spring 쪽 정책).

### 4.5 최종 결과

파이프라인이 반환하는 값 (`트러블슈팅- Elice API.md` 4장 기준, 아래 6장에서 실제 DTO로 구체화):

- 처리 결과: `PLACE_RESOLVED` / `NEEDS_CONFIRMATION` / `NO_PLACE`
- 콘텐츠 요약, 카테고리
- 장소명·지점명, 장소 제공자 식별자, 주소·좌표
- 사용자 확인이 필요한 경우 질문과 선택지

## 5. 실패 처리

`extraction.type.FailureStage`(이미 팀원이 정의함, 4단계)를 그대로 쓰되, 3~5단계(장소 검색/확신도 판정)는 이 파이프라인에서 별도로 처리한다.

| 단계 | 실패 시 |
|---|---|
| METADATA_FETCH | YouTube API 실패 (비공개/삭제 영상 등) |
| VIDEO_ACCESS | Gemini가 영상 자체에 접근 못함 |
| GEMINI_CALL | API 호출 실패 (429 할당량 초과, 503 과부하 — 오늘 둘 다 실제로 겪음) |
| RESPONSE_MAPPING | 구조화 출력 파싱 실패 |
| (신규) PLACE_SEARCH | 장소검색 API 실패/타임아웃 — `FailureStage`에 추가 필요할 수 있음 |

LLM 응답이 형식에 안 맞으면 1회 재시도 후 실패 처리 (카테고리 `기타`, 장소 없음, 확신도 0).

## 6. 패키지/클래스 구조 (제안)

`backend/Remembrall/src/main/java/com/ktc/chungnam3/remembrall/` 아래, 이미 있는 `extraction` 패키지(팀원 작성 DTO)와 나란히 새 패키지를 만든다.

```
remembrall/
├── extraction/                          (이미 있음 — 건드리지 않음)
│   ├── dto/  (YouTubeContentExtractionResultDto, PlaceCandidateDto, TemporalInfoDto, EvidenceDto, FailureInfoDto, AnalysisMetadataDto)
│   └── type/ (ExtractionStatus, EvidenceSource, FailureStage)
│
└── save/                                (신규 — 이 문서의 범위)
    ├── SavePipelineService.java         — 전체 흐름 조율 (4.1~4.5 순서대로 호출)
    ├── youtube/
    │   └── YoutubeMetadataClient.java   — YouTube Data API v3 REST 호출
    ├── analysis/
    │   └── VideoContentAnalyzer.java    — Spring AI로 Gemini 호출, YouTubeContentExtractionResultDto 생성
    ├── place/
    │   ├── PlaceSearchClient.java       — 장소검색 API 연동 (제공사 미정)
    │   └── PlaceResolver.java           — 후보 확정/재검색/애매함 판단
    ├── confirm/
    │   └── ConfirmPolicy.java           — 되묻기 여부 판정 (무상태, alreadyAsked 파라미터로 받음)
    └── dto/
        ├── SavePipelineResultDto.java   — 최종 반환 (status, summary, category, place, confirm 등 — 5장 내용)
        ├── ResolvedPlaceDto.java        — 확정된 장소 (name, branchName, address, lat/lng, providerId)
        └── ConfirmRequestDto.java       — 되묻기 질문 + 선택지

com.ktc.chungnam3.remembrall.save.dto.SavePipelineStatus (enum): PLACE_RESOLVED, NEEDS_CONFIRMATION, NO_PLACE
```
