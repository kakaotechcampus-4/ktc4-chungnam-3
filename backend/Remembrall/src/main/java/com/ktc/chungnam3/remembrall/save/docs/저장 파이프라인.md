# 저장 파이프라인

"저장담당" 역할의 구현 설계. 무엇을 반환해야 하는지(계약)는 `저장담당 요구 사항.md`에 있고, 이 문서는 어떻게 만들 것인지를 다룬다.

## 1. 왜 "에이전트"가 아니라 "파이프라인"인가

> **팀 결정**: 장소 후보 판단과 재검색은 도구를 쥐어줘도 AI가 고를 여지 없이 정해진 순서(메타데이터 조회 → 영상 분석 → 장소 검색 → 확신도 판정)대로 수행할 수밖에 없는 절차라, 에이전트로 보기 어렵다고 판단해 저장 쪽은 파이프라인으로 정했다. LLM 호출은 "영상 분석" 한 단계뿐이고, 그마저도 고정된 프롬프트·스키마 호출이지 도구를 선택하는 루프가 아니다.

"꺼내기 에이전트"는 여전히 진짜 에이전트다 (지오펜스 트리거 이후 가설을 세우고 도구를 골라 쓰고 계획을 바꾸는 자율 루프). 저장 쪽만 바뀐 것이다.


## 2. 하는 일/ 안하는 일

| 한다 | 안 한다 |
|---|---|
| 영상 분석 | DB 저장 (Spring 코어) |
| 장소 탐색·검증 (좌표 확보) | 트리거 생성/저장 (Spring 코어) |
| 확신도 판정 → 필요시 사용자 확인 요청 | 알림 발송, 꺼내기 판단 (꺼내기 에이전트) |
| 위 결과를 Spring 코어에 반환 | 원본 영상·음성·전체 자막 저장 (정책상 금지) |
| | 장소 없는 저장물의 재노출 (꺼내기 에이전트가 다른 저장물과 함께 붙여서 노출 — 저장 파이프라인은 `NO_PLACE`를 정직하게 반환하기만 하면 됨) |

## 3. 동작 흐름

1. **유튜브 URL 입력**
2. **지원 형식 검증** (Spring, 파이프라인 호출 전) — 지원 목록에 없는 링크는 여기서 바로 거절하고 끝 (`지원하지 않는 형식`)
3. **메타데이터 조회** — YouTube Data API v3 (`videos.list`, `commentThreads.list`)
4. **영상 분석** — Vertex AI Gemini에 영상 URL 직접 전달, 구조화 출력으로 요약·장소후보·기간정보 추출
5. **장소 탐색·검증** — 장소 후보를 LocationIQ로 검색해 좌표·주소 확보
6. **판정** — 다음 중 하나로 결과가 갈린다
   1. 장소 1건으로 확정됨 → `PLACE_RESOLVED`
   2. 후보가 있으나 2~3개로 좁혀짐 → `NEEDS_CONFIRMATION` (질문+선택지 포함)
   3. 후보가 있으나 확정 불가, 또는 애초에 후보 없음 → `NO_PLACE`
7. **결과 반환** → Spring이 형식·필수값 검증 → 장소가 확정된 경우에만 위치 트리거 생성 → DB 저장

**핵심 원칙**
- 정보가 없으면 만들지 않는다 — 좌표를 추측해서 채우지 않는다. 트리거 0개(`NO_PLACE`)는 정상 경로다.
- 되묻기는 콘텐츠당 최대 1회. 파이프라인은 무상태라 "이미 물어봤는지"는 Spring이 매 호출마다 넘겨줘야 한다.
- 기간(일정) 기반 트리거는 MVP 범위 밖. 기간 정보는 추출은 하되(`TemporalInfoDto`) 트리거로 연결하지 않는다.

## 4. 단계별 요약

| 단계 | 내용 |
|---|---|
| 0. 지원 형식 검증 | 지원 플랫폼·형식을 코드 목록으로 관리. 목록 밖 링크는 파이프라인 호출 전에 Spring이 바로 거절 (장소 없음과는 다른 상태로 구분) |
| 1. 메타데이터 조회 | YouTube Data API v3를 API 키로 REST 직접 호출 (`videos.list`, `commentThreads.list`). 채널 소유자가 단 댓글만 필터링 — 주소를 답글로 남기는 경우가 많아 유용 |
| 2. 영상 분석 | Vertex AI Gemini에 유튜브 URL을 영상으로 직접 전달(다운로드 안 함), 구조화 출력(JSON 스키마)으로 요약·장소후보·기간정보·근거를 한 번에 받음. Spring AI(`GoogleGenAiChatModel`)로 구현·검증 완료 |
| 3. 장소 탐색·검증 | 장소 후보를 **LocationIQ**로 검색해 좌표 확보 (좌표 영구 저장 가능한 제공사로 선정). 지도 "표시"는 Google SDK — 좌표 확보와 분리. 장소는 자체 ID로 식별해 제공사 교체에 대비 |
| 4. 확신도 판정 | 확신도가 낮고 후보를 2~3개로 좁힐 수 있을 때만 `NEEDS_CONFIRMATION`. 미응답 시 상위 지역으로 저장, 다시 묻지 않음 |

## 5. 실패 처리

| 단계 (`FailureStage`) | 실패 사유 | 재시도 |
|---|---|---|
| METADATA_FETCH | 비공개·삭제된 영상 | 불가 → `FAILED` |
| VIDEO_ACCESS | Gemini가 영상 자체에 접근 못함 | 불가 → `FAILED` |
| GEMINI_CALL | API 호출 실패 (429 할당량, 503 과부하 등) | 가능 → 재시도 |
| RESPONSE_MAPPING | 구조화 출력 파싱 실패 (1회 재시도 후에도 실패 시) | 불가 → `FAILED` |
| PLACE_SEARCH *(신규 제안)* | LocationIQ 실패/타임아웃 | 가능 → 재시도 |

> **결정**: `ExtractionStatus`(`SUCCESS`/`PARTIAL`/`FAILED`)는 "결과를 쓸 수 있는가"만 답하도록 그대로 두고, "재시도할 가치가 있는가"는 별도 축이라 `FailureInfoDto.retryable`(boolean) 필드로 표현한다. 두 질문을 하나의 enum에 합치면 조합마다 값이 늘어나므로, 상태값을 늘리는 대신 필드를 분리했다. 위 표의 "재시도" 칸이 각 `FailureStage`별 `retryable` 값을 정하는 기준이 된다.

## 6. YouTube API 정책 준수

YouTube Data API v3로 얻는 메타데이터·댓글은 OAuth 없이 API 키로만 조회하므로 개발자 정책상
"Non-Authorized Data"에 해당한다. 아래 기준을 지킨다 (출처: YouTube API Services Developer Policies).

| 기준 | 내용 |
|---|---|
| 보관 기간 | 원본 제목·설명·댓글은 최대 30일까지만 임시 저장. 이후엔 재조회로 갱신하거나 삭제 |
| 삭제 요청 | 사용자가 콘텐츠 삭제를 요청하면 관련 원본 데이터를 7일 이내 삭제 |
| 자체 분석 표시 | `summary`·장소 후보처럼 우리가 만든 분석 결과는 "AI가 생성한 자체 분석"임을 화면에 명확히 표시 (YouTube가 준 데이터인 것처럼 보이지 않게) |
| 광고 제한 | YouTube API 데이터가 노출된 화면에는, 그 데이터를 빼도 남을 독립적 콘텐츠(장소·트리거·알림 등)가 있어야 광고 판매 가능. 구독 등 앱 자체 유료화는 제한 없음 |
| 출처 표시 | 썸네일·제목 등 YouTube 원본을 그대로 보여줄 땐 YouTube가 출처임을 표시 (YouTube 브랜드 가이드라인 준수) |

**설계에 미치는 영향**: DB에는 원본 메타데이터·댓글 전문이 아니라 우리가 만든 짧은 요약(`summary`)과
검증된 장소 정보만 저장하는 게 기본 원칙(이미 `카테켐프로젝트 개요.md` 7장과 일치). `EvidenceDto.detail`
같은 근거 필드도 원문 전체가 아니라 짧은 발췌로 남긴다. 원본 제목 등을 30일 넘게 보관해야 하는 경우가
생기면, 주기적으로 재조회해 갱신하는 절차가 `SavePipelineService` 설계에 포함되어야 한다.

## 7. 패키지 구조

`backend/Remembrall/src/main/java/com/ktc/chungnam3/remembrall/` 아래, 기존 `extraction` 패키지(팀원 작성 DTO) 옆에 신설.

```
remembrall/
├── extraction/                        (기존 — DTO/enum, 건드리지 않음)
│
└── save/
    ├── SavePipelineService.java       전체 흐름 조율                
    ├── youtube/
    │   ├── YoutubeMetadataClient.java YouTube Data API v3 REST 호출          
    │   └── YoutubeUrlParser.java      URL → videoId                         
    ├── analysis/
    │   └── VideoContentAnalyzer.java  Spring AI로 Gemini 호출 → 추출 DTO 생성
    ├── place/
    │   ├── PlaceSearchClient.java     LocationIQ 연동, (자체ID,lat,lng,주소)로 정규화 
    │   └── PlaceResolver.java         후보 확정/재검색/애매함 판단              
    ├── confirm/
    │   └── ConfirmPolicy.java         되묻기 여부 판정                
    └── dto/
        ├── SavePipelineResultDto.java 최종 반환 (status/summary/place/confirm)
        ├── ResolvedPlaceDto.java      확정 장소 (name, address, lat/lng)
        └── ConfirmRequestDto.java     되묻기 질문
```
