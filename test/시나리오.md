
# 작성 규칙

- **기준**: `develop` `7413fc1` (2026-10-12) 구현 상태
- **ID**: `도메인-번호` 형식 (예: `AUTH-03`)
- **우선순위**
  - P0: 핵심 흐름과 보안. 실패하면 릴리스할 수 없음
  - P1: 오류 처리와 예외 흐름

- **상태**

# EVT: 위치 이벤트

### 서버 동작

- 인증 오류는 401, 요청 형식 오류는 400입니다.
- 인증과 형식 검사를 통과하면, 아래 조건에 걸려 이벤트를 무시하더라도 **항상 202**를 반환합니다. 서버는 다음 순서로 검사하고, 하나라도 걸리면 실행 기록을 만들지 않습니다.
  1. 요청 회원에게 해당 `placeId`의 트리거가 있는가
  2. 같은 트리거에 같은 `triggerEventId`의 실행 기록이 이미 있는가 (중복)
  3. `eventOccurredAt`이 30분보다 오래됐는가
  4. 요청 회원의 실행 기록이 최근 10분 안에 생성됐는가 (쿨다운)
  5. 위치기반서비스 동의(`LOCATION_BASED_SERVICE`)가 유효한가
- 현재 꺼내기 에이전트는 임시 구현(`StubRecallAgent`)이라 항상 `NO_ACTION`을 반환합니다. 그래서 정상 이벤트여도 **알림이 생기지 않습니다.**

### 판정 기준

- 알림 생성이 아니라 **`recall_execution` 실행 기록 생성 여부**로 판정합니다. 정상 처리되면 `status: COMPLETED`, `result: NO_ACTION`인 행이 하나 생깁니다.
- 실행 기록을 조회하는 API가 없으므로 Bruno 응답(202)만으로는 통과 처리하지 않습니다. 실행 기록은 DB를 직접 확인하거나 백엔드 통합 테스트(`LocationEventIntegrationTest`)로 확인합니다.
- **확인** 열의 뜻은 다음과 같습니다.
  - Bruno: 응답만으로 판정
  - Bruno + DB: 202 확인 후 `recall_execution` 확인
  - 통합 테스트: Bruno와 DB로는 원인을 구분할 수 없음

### 공통 사전 조건 (EVT-01~07, 12~14)

각 시나리오는 검사하려는 조건 하나만 비정상으로 두고, 나머지는 아래처럼 정상으로 준비합니다. 그래야 다른 조건에 먼저 걸려서 잘못 통과하는 일이 없습니다.

- 요청 회원이 위치기반서비스에 동의한 상태
- 요청 회원에게 해당 `placeId`의 트리거가 있음
- 요청 회원의 실행 기록이 최근 10분 안에 없음. 쿨다운 간섭을 피하려고 **시나리오마다 다른 회원을 사용**합니다.
- `eventOccurredAt`은 현재 시각, `triggerEventId`는 새 UUID
