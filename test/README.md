# REMEMBRALL QA 운영 계획

이 문서는 REMEMBRALL의 테스트 범위와 운영 방식을 정리한 문서다.  
QA의 목표는 단순히 API가 응답하는지 확인하는 데 그치지 않고, 사용자가 콘텐츠를 저장한 뒤 적절한 상황에서 다시 제안받는 전체 흐름의 품질을 관리하는 것이다.

현재는 QA 체계를 설계하는 단계다. 아래 디렉터리와 자동화는 구현 순서에 따라 추가한다.

## 1. QA 목표

- 핵심 사용자 흐름이 릴리스마다 정상적으로 동작하는지 확인한다.
- 정상 케이스뿐 아니라 실패, 권한 거부, 중복 요청과 외부 서비스 장애를 검증한다.
- API 변경과 테스트 변경을 같은 PR에서 함께 관리한다.
- 반복 가능한 테스트는 자동화하고, 실제 기기가 필요한 테스트는 체크리스트로 관리한다.
- 테스트 결과와 알려진 결함을 근거로 릴리스 가능 여부를 판단한다.

## 2. 역할과 책임

### PM · QA 담당

- 테스트 범위와 우선순위를 정한다.
- 핵심 시나리오와 릴리스 통과 기준을 관리한다.
- 결함의 심각도와 수정 우선순위를 결정한다.
- 회귀 테스트 결과와 미해결 결함을 확인하고 릴리스 여부를 판단한다.

### 개발자

- 변경한 코드의 단위·통합 테스트를 작성한다.
- API를 추가하거나 변경할 때 Bruno 요청과 검증 항목을 함께 수정한다.
- 버그 수정 시 해당 문제가 다시 발생하지 않도록 재현 테스트를 추가한다.
- PR을 올리기 전에 담당 영역의 테스트를 실행한다.

## 3. 테스트 구분

| 구분 | 목적 | 주 도구 | 실행 시점 |
| --- | --- | --- | --- |
| 정적 검사 | 타입·코드 규칙 오류 확인 | TypeScript, ESLint | PR마다 |
| 단위 테스트 | 개별 정책과 비즈니스 로직 검증 | JUnit, 프론트 테스트 도구 | PR마다 |
| 통합 테스트 | DB, 인증, Repository와 Spring 설정 검증 | Spring Boot Test, Testcontainers | PR 또는 `develop` 반영 후 |
| API 테스트 | HTTP 계약, 인증, 오류 응답과 상태 변화 검증 | Bruno | PR 및 회귀 테스트 |
| 화면 테스트 | 화면 상태와 사용자 입력 검증 | 프론트 테스트 도구, 수동 테스트 | 기능 완료 시 |
| 실제 기기 테스트 | 공유 시트, 딥링크, 권한, 위치, 푸시 검증 | Android 실제 기기·에뮬레이터 | 기능 완료 및 릴리스 전 |
| 비기능 테스트 | 보안, 성능, 접근성, 호환성 확인 | 체크리스트 및 전용 도구 | 릴리스 전 |

Bruno는 API 계약과 반복 회귀 테스트에 사용한다. 공유 시트, 지오펜스, 앱 종료 상태의 푸시처럼 OS 동작에 의존하는 기능은 Bruno 결과만으로 통과 처리하지 않는다.

## 4. QA 디렉터리 계획

```text
qa/
├── README.md
├── bruno/
│   ├── bruno.json
│   ├── environments/
│   │   ├── local.bru
│   │   └── staging.bru
│   ├── 00-health/
│   ├── 01-auth/
│   ├── 02-content-save/
│   ├── 03-confirmation/
│   ├── 04-recall/
│   └── 99-regression/
├── test-cases/
│   ├── MVP-저장.md
│   ├── MVP-꺼내기.md
│   └── 앱-권한과알림.md
└── checklists/
    ├── PR-QA.md
    └── RELEASE-QA.md
```

- `bruno/`: Git으로 공유하고 CLI에서도 실행할 API 컬렉션
- `test-cases/`: 기능별 사전 조건, 절차, 기대 결과
- `checklists/`: PR과 릴리스에서 빠짐없이 확인할 항목
- 실행 결과와 리포트 파일은 Git에 커밋하지 않고 CI artifact로 보관한다.

## 5. Bruno 운영 규칙

### Git 관리

- Bruno 컬렉션은 현재 모노레포의 `qa/bruno/`에서 관리한다.
- API 구현과 해당 API의 Bruno 테스트는 가능하면 같은 PR에 포함한다.
- 요청 이름은 행동과 기대 결과가 드러나게 작성한다.
  - 예: `정상 로그인 - 200`
  - 예: `잘못된 카카오 토큰 - 401`
- 컬렉션은 번호가 붙은 도메인 폴더로 구분하고, 폴더 안에서는 정상·실패 케이스를 함께 관리한다.

### 환경과 비밀정보

- `baseUrl`처럼 공개 가능한 설정만 환경 파일에 둔다.
- 카카오 토큰, JWT, YouTube API 키, Gemini 인증 정보, LocationIQ 키와 FCM 자격증명은 커밋하지 않는다.
- 로컬에서는 Bruno secret 또는 프로세스 환경변수를 사용한다.
- CI에서는 GitHub Actions Secrets를 사용한다.
- 비밀정보가 Git에 올라간 경우 파일만 지우지 말고 즉시 해당 키를 폐기하고 재발급한다.

### API별 기본 검증 항목

모든 API는 가능한 범위에서 다음 항목을 검증한다.

- HTTP 상태 코드
- 응답 헤더와 콘텐츠 타입
- 필수 필드의 존재 여부와 타입
- 상태별 필드의 `null` 또는 빈 배열 규칙
- 인증과 사용자별 접근 권한
- 필수값 누락, 빈 문자열과 잘못된 형식
- 존재하지 않는 리소스
- 중복 요청과 재시도
- 예상하지 않은 상태 코드
- 허용 가능한 응답 시간

요청 간 흐름이 있는 경우 앞 요청의 응답 값을 다음 요청의 runtime variable로 전달한다. 예를 들어 로그인 후 받은 토큰으로 인증 API를 호출하고, 갱신과 로그아웃까지 한 시나리오로 검증한다.

## 6. 핵심 테스트 시나리오

### 6.1 인증

- 정상 카카오 로그인
- 잘못되거나 누락된 카카오 액세스 토큰
- 정상 access token으로 보호 API 접근
- 만료되거나 변조된 access token
- 정상 refresh와 잘못되거나 만료된 refresh token
- 로그아웃 후 refresh token 재사용 차단
- 동일 기기 재로그인과 기기 정보 갱신
- 다른 사용자의 데이터 접근 차단

실제 카카오 서비스에 의존하는 테스트는 일반 PR 테스트와 분리한다. PR에서는 안정적인 테스트 대역을 사용하고, 실제 연동 테스트는 staging에서 수동 또는 정기적으로 실행한다.

### 6.2 콘텐츠 저장

- 정상 YouTube Shorts URL
- 잘못된 URL과 지원하지 않는 형식
- 비공개·삭제 영상
- 장소 한 곳이 확정되는 경우
- 장소 후보 2~3개로 사용자 확인이 필요한 경우
- 장소가 없는 정상 콘텐츠
- Gemini 호출 또는 응답 변환 실패
- 장소 검색 실패와 재시도 가능 여부
- 같은 URL의 중복 저장
- `SUCCESS`, `PARTIAL`, `FAILED` 반환 규칙
- 목록 필드가 `null`이 아닌 빈 배열로 반환되는지 확인

다음 세 결과는 서로 다른 상태로 검증한다.

```text
장소 없음 = 정상 분석 결과
분석 실패 = 오류 결과
장소 확인 필요 = 사용자 입력 대기
```

### 6.3 장소 확인

- 유효한 `candidateId` 선택
- 존재하지 않는 후보 선택
- 다른 콘텐츠에서 발급된 후보 ID 사용
- 이미 확정된 콘텐츠에 대한 중복 확인
- 콘텐츠당 확인 요청 1회 제한
- 사용자가 응답하지 않았을 때의 처리

`candidateId`는 한 번의 추출 결과 안에서만 유효한 임시 식별자로 취급한다.

### 6.4 꺼내기와 알림

API에서 확인할 항목:

- 정상 지오펜스 진입 이벤트
- 동일 이벤트 중복 전송
- 비활성 또는 다른 사용자의 트리거
- `PROPOSE`와 `NO_ACTION`
- 실행 중인 요청의 중복 처리
- 최근 알림과 중복 알림 방지

실제 기기에서 확인할 항목:

- 앱 실행 중·백그라운드·종료 상태의 푸시 수신
- 알림을 눌렀을 때 올바른 상세 화면 이동
- 위치·알림 권한 거부와 권한 자동 회수
- 네트워크 단절 후 복구
- 앱 콜드 스타트 시 보류 이벤트 처리
- FCM 토큰 갱신

## 7. CI 운영 계획

### PR에서 실행

빠르고 외부 환경에 덜 의존하는 검사만 실행한다.

- 백엔드 단위 테스트
- 프론트 lint와 TypeScript 타입 검사
- Bruno smoke 테스트
- 비밀정보 유출 검사

목표 실행 시간은 5분 이내로 잡는다.

### `develop` 반영 후 실행

- 백엔드 통합 테스트
- 전체 Bruno API 회귀 테스트
- 테스트 결과 리포트 생성
- 리포트를 GitHub Actions artifact로 보관

### 릴리스 후보에서 실행

- staging 대상 Bruno 전체 테스트
- 실제 Android 기기 체크리스트
- 저장부터 알림까지의 핵심 흐름 테스트
- 미해결 결함과 테스트 제외 항목 검토
- PM의 최종 릴리스 승인

YouTube, Gemini, 장소 검색과 카카오 같은 외부 서비스의 실제 호출은 PR 필수 검사에서 분리한다. 외부 장애나 할당량 문제 때문에 정상적인 코드 변경이 차단되지 않도록 mock 기반 테스트와 실제 연동 테스트를 구분한다.

## 8. 결함 관리

### 심각도

| 등급 | 기준 | 예시 |
| --- | --- | --- |
| S0 | 보안 사고, 데이터 유출·삭제 또는 서비스 전체 장애 | 다른 사용자의 저장물 노출 |
| S1 | 핵심 흐름을 완료할 수 없고 우회 방법이 없음 | 콘텐츠 저장이 항상 실패함 |
| S2 | 일부 기능이 잘못되지만 우회할 수 있음 | 특정 URL 형식만 저장 실패 |
| S3 | 경미한 UI·문구·사용성 문제 | 정렬, 여백 또는 안내 문구 오류 |

### 버그에 기록할 내용

- 발생 환경과 앱·서버 버전
- 사전 조건
- 재현 절차
- 실제 결과와 기대 결과
- 재현 빈도
- 화면 캡처·영상 또는 관련 로그
- 관련 요청과 응답에서 비밀정보를 제거한 내용
- 심각도, 담당자와 목표 수정 시점

## 9. 릴리스 통과 기준

- S0와 S1 미해결 결함이 없다.
- 저장 및 꺼내기 핵심 시나리오가 모두 통과한다.
- 전체 회귀 테스트의 95% 이상이 통과한다.
- 실패하거나 제외한 테스트에는 사유, 영향과 승인자가 기록되어 있다.
- 새로 추가되거나 변경된 API에 Bruno 테스트가 있다.
- 실제 Android 기기에서 공유, 저장, 위치 진입, 알림 확인 흐름이 통과한다.
- 로그와 응답에 토큰, API 키와 개인정보가 노출되지 않는다.

기능이 완성되지 않은 단계에서는 미구현 항목을 실패로 집계하지 않고 `미구현`으로 구분한다. 구현이 완료된 기능만 릴리스 통과율 계산에 포함한다.

## 10. 도입 순서

### 1단계 — QA 기반

- QA 문서와 테스트 케이스 템플릿 작성
- 결함 심각도와 릴리스 통과 기준 합의
- Bruno local·staging 환경 및 비밀정보 규칙 설정

### 2단계 — 현재 API 자동화

- 인증 API Bruno 컬렉션 작성
- 정상·실패 응답 assertion 추가
- 로그인, 갱신, 로그아웃의 요청 연결

### 3단계 — CI 연결

- 백엔드 단위 테스트와 프론트 정적 검사 실행
- Bruno smoke 테스트 실행
- 테스트 리포트 artifact 보관

### 4단계 — MVP 기능 확장

구현 순서에 맞춰 테스트를 함께 추가한다.

```text
URL 정규화
→ 콘텐츠 저장
→ Gemini 분석
→ 장소 검증
→ 사용자 확인
→ 지오펜스
→ 꺼내기 에이전트
→ FCM 알림
```

### 5단계 — 릴리스 리허설

- 개발에 참여하지 않은 팀원이 신규 사용자 관점에서 전체 흐름을 수행한다.
- PM은 테스트 결과, 미해결 결함과 제외 항목을 검토한다.
- 통과 기준을 충족하면 릴리스하고, 충족하지 못하면 수정 범위와 재검증 일정을 정한다.

## 11. 현재 우선순위

1. 인증 API Bruno 컬렉션 만들기
2. PR QA 체크리스트 만들기
3. 백엔드 테스트와 프론트 정적 검사를 실행하는 팀 CI 추가하기
4. 저장 API가 구현되는 시점부터 API와 Bruno 테스트를 같은 PR로 관리하기
5. 위치·푸시 기능 구현 전에 실제 기기 테스트 환경과 담당 기기를 정하기
